## 2. What it is

The hierarchical distributed database mapping human-readable names to IP addresses (and other records), with caching resolvers at every level.

## 3. Why it exists

Names must resolve to the right place, quickly, during failures.

## 4. The engineering problem it solves

Without DNS you hardcode IPs — every failover, migration, and CDN cutover breaks; DNS is also a frequent root cause of "everything is down but nothing changed (CDN TTL expired)".

## 5. How it works internally

Resolution chain (recursive resolver → root → TLD → authoritative); record types: A/AAAA (address), CNAME (alias), ALIAS/ANAME (apex alias), MX (mail), TXT (verification), SRV (service+port), NS. TTL governs cache lifetime (30s–24h); negative caching; round-robin and latency-based/failover routing policies (Route 53/Cloud DNS); DNSSEC signs records (integrity). Common failure: TTL set to 1h during an outage pointing at the dead IP (launch day TTL should be ≤60s until stable).

## 6. Architecture and design principles

Stub resolver (OS/app) -> recursive resolver (ISP/1.1.1.1/8.8.8.8) -> root -> TLD -> authoritative; TTL-bound caches at every level; failover/latency routing policies at the authoritative layer.

**Design principles for this category:** Choose transport by semantics (ordering, latency, loss tolerance); name everything through discovery, never literals.

## 7. When to use it

N/a — DNS always exists; decisions are TTL/routing/DNSSEC.

## 8. When NOT to use it

Notice product-limitation: DNS not usable for sub-minute cutover — use accelerators/Anycast for that.

**Alternatives:** global accelerator (health-checked, L4), service mesh, mDNS/internal discovery (K8s Services).

## 9. Implementation strategies

```
Route 53 failover policy: PRIMARY health-checked record → ALB; SECONDARY → static S3 status page
TTL: 60s for app endpoints; 300-3600s for stable infra; 5s for migration cutovers
_ dig +trace app.example.com      # see the actual delegation chain
```

## 10. Production-grade implementation

**Scenario:** Primary region loss: health check marks record unhealthy in 30s; resolver caches refresh within TTL 60s; traffic shifts to us-east-1; TTL 300s would have meant 5 extra minutes of outage — TTL discipline paid off.

**To reach production grade, combine the implementation in section 9 with these non-negotiables:**

- Wire the section 19 signals into dashboards and alerts *before* the rollout — an unmeasured control is decorative.
- Bake the control into the pipeline, not the runbook: IaC/CI enforces it on every deploy; humans should not be the enforcement layer (`#6 CI/CD`, `#104 Infrastructure as Code`).
- Load and failure-test it at 2x expected traffic, in staging with production-like data volume, before declaring it done (`#26 Query Optimization`, `#91 Latency`).
- Roll out behind a canary or flag with automatic rollback on SLO burn (`#53 Canary Releases`, `#51 Feature Flags`), and document the rollback path in the runbook.
- Verify the dependent data path explicitly: migrations, secrets, certificates, and IAM policies ship with the same change.

## 13. Distributed-system considerations

The network is the shared resource: ordering, loss, partitions, and clock skew are not pathologies — they are the medium. Design with them.

## 14. AI/ML/LLM application examples where relevant

Provider endpoint failover via DNS/global accelerator — health-checked subdomain per region.

## 15. Security considerations

DNSSEC where possible; registrar lock; monitor for unauthorized NS/A changes.

## 16. Performance considerations

Protocol choice is throughput choice: HTTP/2 multiplexing, gRPC streaming, QUIC vs TCP trade loss sensitivity against HOL blocking.

## 17. Common mistakes

Manual IP entries; TTL 86400 everywhere; single authoritative provider; dangling CNAMEs (self-serve subdomain takeover); no health checks on A records; expiry unmanaged (auto-renew domains).

## 18. Anti-patterns

The field anti-patterns for this topic are the same ones listed in section 17 — they cluster into four recurring shapes. Review code and incidents against these **red flags**:

- An unbounded resource (queue, pool, retry loop, cache, response) somewhere on the path — production favors bounded shapes everywhere (`#44 Backpressure`, `#1 Rate Limiting`).
- A correctness control without its verification: retries without idempotency, locks without TTL/fencing, caches without invalidation plans, migrations without rollback.
- Silent degradation: errors swallowed, fallback paths unmonitored, `success: true` on partial failure.
- A shared failure domain introduced for convenience — hard dependency, cross-tenant leakage, one config for all criticality levels.

If you spot one of these in review, stop and fix it before merging — it will page someone later.

## 19. Monitoring and observability

**Signals to emit:** `dns_resolution_seconds`, NXDOMAIN rate, failover-propagation time

**Also watch:** service-level RED (rate/errors/duration), the dependency trees above and below this control, and cost (`#88 Cost Optimization`). Correlate logs, metrics, and traces via a shared `trace_id` (`#60 Distributed Tracing`, `#66 Observability`).

## 20. Testing strategies

External probes from 3 continents; failover drill (mark primary unhealthy, measure propagation); DNSSEC validation; dangling-record scanner; resolver-cache behavior test.

## 21. Deployment considerations

Protocol/version changes are deploys too: enable H2/H3 at the edge first, verify clients, then simplify origins; DNS/cert changes rehearsed with low TTL.

## 22. Production-readiness checklist

- [ ] Failover routing with independent health checks
- [ ] Low TTL for cutover windows
- [ ] Secondary DNS provider (different network)
- [ ] DNSSEC where supported
- [ ] Monitor with external probes (not just your authoritative)
- [ ] Document delegation
- [ ] Avoid dangling CNAMEs to deprovisioned cloud resources (takeover risk!)
- [ ] Observability wired (metrics above), dashboards linked, alert runbook written
- [ ] Rollback or kill-switch verified < 5 minutes

## 23. Troubleshooting guide

- **Symptom:** TTL too long during cutover (stale IP); TTL too low (resolver load, slight latency); CNAME at apex (illegal — use ALIAS); forgetting to update DNS after LB IP change (control plane does it; manual doesn't); split-horizon misconfig (public resolver vs VPC resolver disagree); DNSSEC broken DS record → SERVFAIL everywhere; registrar lock/expiry (domain hijack risk); DNS as availability dependency (cache + secondary DNS provider).
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
