## 2. What it is

Cross-Site Scripting — injecting attacker-controlled script into pages other users render; stored (persisted in DB, hits everyone), reflected (echoed in the response), or DOM-based (client-side templates write untrusted data into innerHTML).

## 3. Why it exists

Untrusted script executes with your users' authority.

## 4. The engineering problem it solves

A single stored XSS payload in a comment steals every viewer's session, keystrokes, and CSRF tokens; token theft happens *as* the victim, so all their permissions are the attacker's.

## 5. How it works internally

Browser parses HTML; any script in the page executes with the page's origin privileges. Defenses: **context-aware output encoding** (HTML entity, attribute, JS, URL, CSS contexts — different escaping for each), templating engines with autoescaping on by default (Jinja2, React, Vue), **Content Security Policy** (`script-src 'self'` without `unsafe-inline` — kills inline XSS even if injection lands), Trusted Types, disabling inline events, sanitization only for rich HTML (DOMPurify or server-side bleach — never hand-rolled regex), `HttpOnly` cookies so JS can't read the session even on successful injection.

## 6. Architecture and design principles

Rendering layer (templates/SPA) + response headers + cookie flags. CSP report-only first, then enforce.

**Design principles for this category:** Deny by default; least privilege; defense in depth — no single control carries the weight; shift security left into CI.

## 7. When to use it

Always — output encoding is universal.

## 8. When NOT to use it

N/a.

**Alternatives:** n/a (no single control is sufficient — encoding + CSP + HttpOnly is the standard bundle).

## 9. Implementation strategies

```python
# Jinja2: {{ user_comment }} auto-escapes; |safe disables it — audit every use
from bleach.sanitizer import Cleaner
cleaner = Cleaner(tags=["p","b","i","a"], attributes={"a": ["href"]}, protocols=["https"])
safe_html = cleaner.clean(user_html)
```

```nginx
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; report-uri /csp-report" always;
```

## 10. Production-grade implementation

**Scenario:** Community feature shipped comment render with `|safe` + unsanitized HTML → stored XSS stole sessions of 12k users; remediated: autoescape restored, DOMPurify on client, CSP enforced (inline blocked), tokens rotated; 3 days incident + notification.

**To reach production grade, combine the implementation in section 9 with these non-negotiables:**

- Wire the section 19 signals into dashboards and alerts *before* the rollout — an unmeasured control is decorative.
- Bake the control into the pipeline, not the runbook: IaC/CI enforces it on every deploy; humans should not be the enforcement layer (`#6 CI/CD`, `#104 Infrastructure as Code`).
- Load and failure-test it at 2x expected traffic, in staging with production-like data volume, before declaring it done (`#26 Query Optimization`, `#91 Latency`).
- Roll out behind a canary or flag with automatic rollback on SLO burn (`#53 Canary Releases`, `#51 Feature Flags`), and document the rollback path in the runbook.
- Verify the dependent data path explicitly: migrations, secrets, certificates, and IAM policies ship with the same change.

## 12. FastAPI integration where relevant

Templates with autoescape (default for .html); JSON APIs are mostly XSS-immune for the API itself, but SPA consuming them must use `textContent`/`innerText` never `innerHTML`; markdown rendered with `bleach`/`markdown` + sanitizer; `HttpOnly, Secure, SameSite` cookies.

## 13. Distributed-system considerations

Security is global: identity, secrets, and policy must be consistent everywhere the workload runs — one unpatched region or sidecar undoes the rest.

## 14. AI/ML/LLM application examples where relevant

Model output rendered as HTML = XSS vector — render as text or sanitized; CSP blocks inline.

## 15. Security considerations

Autoescape + strict CSP (no unsafe-inline) + HttpOnly cookies.

## 16. Performance considerations

TLS + auth cost ~1-10 ms per request — amortized by keepalive and token caching; never skip payment for security 'perf' reasons without measuring.

## 17. Common mistakes

Regex "sanitizer"; innerHTML with user data; CSP as "we have one, it's report-only"; putting raw user input in `<script>` blocks; trusting markdown as safe by default.

## 18. Anti-patterns

The field anti-patterns for this topic are the same ones listed in section 17 — they cluster into four recurring shapes. Review code and incidents against these **red flags**:

- An unbounded resource (queue, pool, retry loop, cache, response) somewhere on the path — production favors bounded shapes everywhere (`#44 Backpressure`, `#1 Rate Limiting`).
- A correctness control without its verification: retries without idempotency, locks without TTL/fencing, caches without invalidation plans, migrations without rollback.
- Silent degradation: errors swallowed, fallback paths unmonitored, `success: true` on partial failure.
- A shared failure domain introduced for convenience — hard dependency, cross-tenant leakage, one config for all criticality levels.

If you spot one of these in review, stop and fix it before merging — it will page someone later.

## 19. Monitoring and observability

**Signals to emit:** `xss_csp_violations_total`, unsafe-sink count in scans

**Also watch:** service-level RED (rate/errors/duration), the dependency trees above and below this control, and cost (`#88 Cost Optimization`). Correlate logs, metrics, and traces via a shared `trace_id` (`#60 Distributed Tracing`, `#66 Observability`).

## 20. Testing strategies

OWASP ZAP/DAST scan; XSS payload corpus through comment/markdown fields; CSP evaluator (Google CSP Evaluator); Playwright test asserting injected script does not execute; audit `|safe`/innerHTML in code review; stored-XSS E2E on staging.

## 21. Deployment considerations

Treat every change to auth/secrets/TLS as security-sensitive: staged rollout, monitoring on rejection rates, and a documented rollback that also rotates anything exposed.

## 22. Production-readiness checklist

- [ ] Autoescape everywhere
- [ ] Audit every `|safe`
- [ ] CSP without unsafe-inline
- [ ] Sanitize rich HTML with DOMPurify/bleach
- [ ] HttpOnly cookies
- [ ] Trusted Types
- [ ] Security headers scan in CI
- [ ] Observability wired (metrics above), dashboards linked, alert runbook written
- [ ] Rollback or kill-switch verified < 5 minutes

## 23. Troubleshooting guide

- **Symptom:** Autoescape disabled "for convenience"; CSP with `unsafe-inline` (no protection); sanitizing for HTML but rendering into JS context (`const x = "{{ value }}"`) without JS-escaping; DOM XSS via `innerHTML` in a dashboard widget; JSON response consumed with `eval`/`innerHTML` (rare but real); CSP report-only forgotten; markdown parser allowing raw HTML passthrough.
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
