## 2. What it is

A Content Delivery Network is a geographically distributed set of edge servers that cache and serve content close to users, offloading the origin. It combines anycast/BGP routing, a caching tier, TLS termination, and often WAF/DDoS protection.

## 3. Why it exists

The fastest response is the one served closest to the user.

## 4. The engineering problem it solves

Users far from the origin pay full round-trip latency and the origin pays full bandwidth; a viral asset or flash crowd saturates origin capacity and egress costs.

## 5. How it works internally

DNS resolves the CDN hostname and anycast/BGP steers the client to the nearest PoP. The edge hashes a cache key from the URL, query, selected headers, and `Vary` fields: a HIT serves locally and increments `Age`; a MISS fetches the origin, honors `Cache-Control`/`s-maxage`, then stores the object. Revalidation uses `If-None-Match`/`If-Modified-Since`, returning 304 with no body. An edge → regional → origin-shield hierarchy collapses fan-out, `stale-while-revalidate` refreshes in the background, and purges run by URL, prefix, or surrogate tag.

## 6. Architecture and design principles

`client → DNS/anycast → edge PoP → (miss) origin shield → origin`, with TLS terminated at the edge and the origin reachable only from CDN ranges.

**Design principles for this category:** Measure before mutating; the primary is the system of record; correctness invariants belong in constraints and transactions, not app code.

## 7. When to use it

Content is public or cacheable, users are geographically spread, and origin latency or bandwidth dominates.

## 8. When NOT to use it

Responses are authenticated and personalized without a cache-key design, data must revoke in milliseconds, or traffic is low and origin-proximate.

**Alternatives:** edge compute (Workers/Lambda@Edge), regional replicas (`#86 Multi-Region Deployment`), or origin-side reverse proxies (`#4 Reverse Proxies`).

## 9. Implementation strategies

CloudFront essentials (Terraform):

```hcl
resource "aws_cloudfront_distribution" "assets" {
  default_cache_behavior {
    allowed_methods        = ["GET", "HEAD"]
    cached_methods         = ["GET", "HEAD"]
    viewer_protocol_policy = "redirect-to-https"
    target_origin_id       = "origin"
    cache_policy_id        = data.aws_cloudfront_cache_policy.optimized.id
  }
  origin {
    domain_name = "origin.example.com"
    origin_id   = "origin"
    origin_shield { enabled = true, origin_shield_region = "us-east-1" }
  }
}
```

## 10. Production-grade implementation

**Scenario:** A marketplace on 41 PoPs serves images from the edge: `/img/*` p95 in São Paulo falls from 420ms to 85ms. Offload reaches 92%, dropping origin traffic from 18k to 1.4k rps and saving ~$11k/month; hashed filenames stay `immutable` while HTML invalidates on deploy.

**To reach production grade, combine the implementation in section 9 with these non-negotiables:**

- Wire the section 19 signals into dashboards and alerts *before* the rollout — an unmeasured control is decorative.
- Bake the control into the pipeline, not the runbook: IaC/CI enforces it on every deploy; humans should not be the enforcement layer (`#6 CI/CD`, `#104 Infrastructure as Code`).
- Load and failure-test it at 2x expected traffic, in staging with production-like data volume, before declaring it done (`#26 Query Optimization`, `#91 Latency`).
- Roll out behind a canary or flag with automatic rollback on SLO burn (`#53 Canary Releases`, `#51 Feature Flags`), and document the rollback path in the runbook.
- Verify the dependent data path explicitly: migrations, secrets, certificates, and IAM policies ship with the same change.

## 11. Code examples (Python)

CloudFront signed URL for private media (canned policy):

```python
import base64, datetime as dt, json, urllib.parse, os
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding

def signed_url(url: str, expires_in: int = 300) -> str:
    exp = int((dt.datetime.now(dt.timezone.utc) + dt.timedelta(seconds=expires_in)).timestamp())
    policy = json.dumps({"Statement": [
        {"Resource": url, "Condition": {"DateLessThan": {"AWS:EpochTime": exp}}}]})
    key = serialization.load_pem_private_key(os.environ["CF_KEY_PEM"].encode(), password=None)
    sig = base64.b64encode(key.sign(policy.encode(), padding.PKCS1v15(), hashes.SHA1()))
    sep = "&" if "?" in url else "?"
    return (f"{url}{sep}Policy={urllib.parse.quote(policy)}"
            f"&Signature={urllib.parse.quote_from_bytes(sig, safe='-_~')}"
            f"&Key-Pair-Id={os.environ['CF_KEY_ID']}")

print(signed_url("https://d111.cloudfront.net/invoice.pdf"))
```

## 12. FastAPI integration where relevant

hand clients CDN URLs with explicit cache headers:

```python
import os
from fastapi import FastAPI, HTTPException, Response

app = FastAPI()
CDN = os.environ["CDN_BASE"]

@app.get("/media/{asset_id}")
def media(asset_id: str, response: Response) -> str:
    if not asset_id.isalnum():
        raise HTTPException(status_code=400, detail="invalid asset id")
    response.headers["Cache-Control"] = "public, max-age=31536000, immutable"
    return f"{CDN}/assets/{asset_id}.webp"
```

## 13. Distributed-system considerations

Distributed state is the hard part: replicas, shards, and lock holders disagree by milliseconds; correctness must survive that disagreement — single-writer, consensus, or commutative designs.

## 14. AI/ML/LLM application examples where relevant

CDN cannot cache LLM responses with user data — but cache public docs/embed assets; signed URLs for model artifacts.

## 15. Security considerations

Signed URLs, short TTL, tenant-scoped keys — prevent cross-tenant cache hits.

## 16. Performance considerations

DB performance dominates: connection pools, indexes, and lock discipline decide p99 more than any app code change.

## 17. Common mistakes

- Caching authenticated responses without per-user keys or `private`.
- One distribution mixing API and static content with a single TTL.
- Manual purges during incidents instead of pipeline invalidation.
- Ignoring `Vary`, serving the wrong encoding or language variant.

## 18. Anti-patterns

The field anti-patterns for this topic are the same ones listed in section 17 — they cluster into four recurring shapes. Review code and incidents against these **red flags**:

- An unbounded resource (queue, pool, retry loop, cache, response) somewhere on the path — production favors bounded shapes everywhere (`#44 Backpressure`, `#1 Rate Limiting`).
- A correctness control without its verification: retries without idempotency, locks without TTL/fencing, caches without invalidation plans, migrations without rollback.
- Silent degradation: errors swallowed, fallback paths unmonitored, `success: true` on partial failure.
- A shared failure domain introduced for convenience — hard dependency, cross-tenant leakage, one config for all criticality levels.

If you spot one of these in review, stop and fix it before merging — it will page someone later.

## 19. Monitoring and observability

**Signals to emit:** `cdn_cache_hit_ratio`, origin offload %, TTFB edge vs origin

**Also watch:** service-level RED (rate/errors/duration), the dependency trees above and below this control, and cost (`#88 Cost Optimization`). Correlate logs, metrics, and traces via a shared `trace_id` (`#60 Distributed Tracing`, `#66 Observability`).

## 20. Testing strategies

Load test from multiple regions cold and warm, asserting >90% hit ratio and p95 gains; verify `Age`/`X-Cache-Status`; vary unkeyed headers and confirm identical responses; purge in staging and confirm the refetch.

## 21. Deployment considerations

Ship with expand/contract migrations; zero-downtime requires old code on new schema during the roll — never deploy breaking DDL in the same release as the code that depends on it.

## 23. Troubleshooting guide

- **Symptom:** Cache poisoning: an unkeyed header changes the stored response — all users get attacker content.
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
- **Symptom:** Private data leak: authenticated HTML cached `public` under a shared key exposes users to each other.
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
- **Symptom:** Stale after deploy: HTML cached 24h loads deleted JS chunks → blank page.
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
- **Symptom:** Origin shield outage: all PoPs stampede the origin at once.
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
