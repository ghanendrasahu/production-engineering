## 2. What it is

Transport Layer Security — the protocol providing encryption, integrity, and server authentication on the wire, using certificates issued by a chain rooted at a trusted CA.

## 3. Why it exists

Plaintext on the wire is read by everyone between you and the client.

## 4. The engineering problem it solves

Plaintext HTTP (and unauthenticated TLS) exposes credentials and data to anyone on-path (WiFi, ISPs, compromised routers) — TLS is table stakes, and its absence is visible in browsers ("Not Secure").

## 5. How it works internally

Handshake: client hello (versions/ciphers) → server sends cert chain → key exchange (ECDHE) → shared session keys via HKDF → encrypted records (AEAD: AES-GCM/ChaCha20). Certificates: X.509, SAN matching hostname, expiry, chain to root. Session resumption (tickets/IDs) to cut handshake cost. TLS 1.3: 1-RTT (0-RTT with replay risk), forward secrecy mandatory. Modern config: TLS≥1.2, strong ciphers, HSTS, OCSP stapling, automated certs via ACME (Let's Encrypt certbot) or cloud-managed (ACM).

## 6. Architecture and design principles

Terminate at LB/reverse proxy or cloud CDN; optionally re-encrypt to backends (TLS everywhere, including internal mTLS with SPIFFE/mesh).

**Design principles for this category:** Deny by default; least privilege; defense in depth — no single control carries the weight; shift security left into CI.

## 7. When to use it

Always.

## 8. When NOT to use it

N/a (even internal links deserve mTLS in zero-trust).

**Alternatives:** n/a; for service-to-service, prefer mTLS via mesh.

## 9. Implementation strategies

```bash
certbot --nginx -d app.example.com --agree-tos -m ops@example.com
# renewal automated via systemd timer / cron
nginx: listen 443 ssl http2; ssl_protocols TLSv1.2 TLSv1.3; ssl_stapling on;
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
```

```python
# Python: requests/httpx verify by default — NEVER verify=False
import ssl, httpx
httpx.get("https://api.example.com", verify=True, timeout=5.0)
```

## 10. Production-grade implementation

**Scenario:** Cloudflare-proxied app: full TLS (edge cert + origin cert), HSTS preload, auto-renewed every 60 days, OCSP stapling; cert expiry monitor pages at 14 days; an expired cert once took the site down — now impossible unnoticed.

**To reach production grade, combine the implementation in section 9 with these non-negotiables:**

- Wire the section 19 signals into dashboards and alerts *before* the rollout — an unmeasured control is decorative.
- Bake the control into the pipeline, not the runbook: IaC/CI enforces it on every deploy; humans should not be the enforcement layer (`#6 CI/CD`, `#104 Infrastructure as Code`).
- Load and failure-test it at 2x expected traffic, in staging with production-like data volume, before declaring it done (`#26 Query Optimization`, `#91 Latency`).
- Roll out behind a canary or flag with automatic rollback on SLO burn (`#53 Canary Releases`, `#51 Feature Flags`), and document the rollback path in the runbook.
- Verify the dependent data path explicitly: migrations, secrets, certificates, and IAM policies ship with the same change.

## 13. Distributed-system considerations

Security is global: identity, secrets, and policy must be consistent everywhere the workload runs — one unpatched region or sidecar undoes the rest.

## 14. AI/ML/LLM application examples where relevant

TLS to providers and to clients — no plaintext tokens anywhere; HSTS for AI web UIs.

## 15. Security considerations

TLS 1.2+ only; HSTS; verify certificates; no mixed content; ocsp stapling.

## 16. Performance considerations

TLS + auth cost ~1-10 ms per request — amortized by keepalive and token caching; never skip payment for security 'perf' reasons without measuring.

## 17. Common mistakes

HTTP behind LB; certs as secrets stored by hand; manual renewal; wildcard cert shared everywhere (blast radius); HSTS without understanding it's sticky (browsers pin you); disabling verification "temporarily"; RC4/3DES legacy ciphers left enabled "for old clients".

## 18. Anti-patterns

The field anti-patterns for this topic are the same ones listed in section 17 — they cluster into four recurring shapes. Review code and incidents against these **red flags**:

- An unbounded resource (queue, pool, retry loop, cache, response) somewhere on the path — production favors bounded shapes everywhere (`#44 Backpressure`, `#1 Rate Limiting`).
- A correctness control without its verification: retries without idempotency, locks without TTL/fencing, caches without invalidation plans, migrations without rollback.
- Silent degradation: errors swallowed, fallback paths unmonitored, `success: true` on partial failure.
- A shared failure domain introduced for convenience — hard dependency, cross-tenant leakage, one config for all criticality levels.

If you spot one of these in review, stop and fix it before merging — it will page someone later.

## 19. Monitoring and observability

**Signals to emit:** `tls_handshake_failures_total`, `cert_expiry_days` (min)

**Also watch:** service-level RED (rate/errors/duration), the dependency trees above and below this control, and cost (`#88 Cost Optimization`). Correlate logs, metrics, and traces via a shared `trace_id` (`#60 Distributed Tracing`, `#66 Observability`).

## 20. Testing strategies

`testssl.sh`/`ssllabs` scan; renewal drill (force-renew staging); expiry alert test; curl verification in smoke tests; verify HSTS header; chaos test: deploy an expired cert in staging and confirm monitor pages.

## 21. Deployment considerations

Treat every change to auth/secrets/TLS as security-sensitive: staged rollout, monitoring on rejection rates, and a documented rollback that also rotates anything exposed.

## 22. Production-readiness checklist

- [ ] TLS 1.2/1.3 only
- [ ] Automated ACME issuance + renewal with monitoring
- [ ] HSTS + preload
- [ ] OCSP stapling

## 23. Troubleshooting guide

- **Symptom:** Expired cert → total outage (most common TLS incident); mixed content (http assets on https page); self-signed/unknown CA on internal service without pinning → "worked in dev, fails in prod"; TLS 1.0 on old clients; TLS termination at LB but plaintext internally and the LB is in the same trust zone as the app (accepted but document it); cert valid but hostname mismatch (SAN missing); certbot renewal cron silently broken; 0-RTT replay on state-changing endpoints.
  **Check:** the failure modes in section 5 and the anti-patterns in section 18; confirm configuration against section 9/10.
  **Fix:** apply the matching best practice in section 18, then re-verify with section 20 (tests) and section 19 (metrics).
